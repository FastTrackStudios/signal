# TONE3000

Browsing, downloading and playing captures from
[TONE3000](https://www.tone3000.com) — the large public library of NAM
models and impulse responses — from inside the rig, the app and the
plugin.

Before this, choosing a capture meant typing a filesystem path into a
text field (`sidebars.rs`) or setting `FTS_NAM_MODEL` for the plugin.

## The shape

```text
                    ┌──────────────────────────────┐
  the catalog ◀────▶ │  signal-tone3000 (engine)    │
   (HTTPS)          │  session · fetch · cache     │
                    │  downloads → NAM library     │
                    └──────────────┬───────────────┘
                                   │ vox (signal-tone3000-proto)
              ┌────────────────────┼────────────────────┐
              │                    │                    │
      browser remote         desktop app          plugin editor
      (wasm, WebSocket)      (native, WS)        (Blitz, memory link)
              └────────────────────┴────────────────────┘
                       signal-tone3000-ui (one component tree)
```

| crate | what it is |
|---|---|
| `crates/signal/tone3000-proto` | the wire contract |
| `crates/signal/tone3000` | the engine half: session, search, artwork, downloads |
| `crates/signal/tone3000-ui` | the tone browser, mounted by every surface |
| `tone3000` (crates.io, MIT) | the API client — OAuth, search, models, downloads |

The engine holds the session and does every fetch. That is the
detachable-GUI rule, and here it is forced twice over: a Blitz plugin
editor cannot host an authorization page (it is a renderer, not a
browser), and the browser remote is served over plain HTTP on the LAN,
where `WebCrypto` — and therefore PKCE — is unavailable. So PKCE is
generated on the engine and a GUI is only ever a courier: it takes a URL
out to the system browser and brings a callback back. No GUI ever sees a
token.

## Signing in

```text
GUI                     engine                  browser            TONE3000
 │  begin_sign_in ────────▶│
 │◀──── authorize_url ─────│  (PKCE minted here)
 │────────────────────────────────── open ────────▶│
 │                                                  │──── authorize ──▶│
 │                         │◀──── GET /tone3000/callback?code&state ───│
 │                         │  verify state, exchange code, persist
 │◀─ status() says signed in
```

The redirect lands on the engine's own HTTP server
(`apps/desktop/src/engine_tone3000.rs`) because nothing else can serve
it: the desktop and plugin GUIs are Blitz, and the browser remote may be
on a different device. The route is derived from the configured redirect
URI, so the URI registered with TONE3000 and the path we serve cannot
drift apart.

`prompt=select_tone` also exists — TONE3000's own picker, which returns a
`tone_id` on the callback (`picked_tone`). It costs no search quota. The
in-app browser uses our own search instead; both work.

## Configuration

| variable | meaning |
|---|---|
| `SIGNAL_T3K_PUBLISHABLE_KEY` | OAuth `client_id`. **Required** — without it every call answers "not configured", which is a different state from signed out and has a different remedy. |
| `SIGNAL_T3K_REDIRECT_URI` | Default `http://localhost:4040/tone3000/callback`. Localhost origins are allowed during development without registration; anything else must be registered against the key. |
| `SIGNAL_T3K_BASE_URL` | Test override (a wiremock URL). |
| `NAM_LIBRARY_PATH` | Where downloads land; defaults to `<config>/nam`. |

Both of the first two can also be baked in at build time under the same
names. The publishable key is not a secret — TONE3000 documents it as
safe for client-side use, and every plugin that ships one hands it to
whoever looks — but it belongs to an account and a set of registered
redirect URIs, so it is configuration rather than source.

State on disk:

```text
<config>/signal/tone3000/session.json   the OAuth session (0600)
<config>/signal/tone3000/images/        artwork, keyed by URL digest
<library>/nam/tone3000/<tone id>/…      downloaded models
<library>/nam/catalog.json              the index, with provenance
```

## Three decisions worth knowing

**Artwork travels as bytes, not URLs.** No two surfaces can fetch a
picture the same way: the browser remote is served
cross-origin-isolated (the keys rig needs `SharedArrayBuffer`), so COEP
blocks the catalog's CDN outright; a Blitz editor has no browser behind
it; an embedded engine serves no HTTP at all. The engine fetches, caches
by URL digest, and sends bytes down the vox link every GUI already has;
the UI renders a `data:` URI. The engine will only fetch URLs a tone
actually carried — otherwise a remote could use it as a proxy into the
LAN.

**Failures ride the payload.** Every listing returns a `TonePage` with an
`error` field rather than a `Result`. Composite returns do not survive
the browser client's schema-compat pass (see `packs-proto::pack_plan`),
and a list screen must anyway distinguish "nothing matched" from "the
request never happened" — a rate limit that renders as an empty shelf
sends the user hunting for a problem that is not there.

**Provenance is written with the file, not after.** Creator, licence and
the tone's URL go into `signal_nam::Provenance` in the same operation
that places the bytes. The API terms forbid stripping attribution, the
download outlives the session that made it, and "record it later" never
happens.

## The models endpoint serves one architecture at a time

It defaults to v1 and has no "all" value, so the obvious single call
silently drops half of a tone that has both. `tone_detail` asks per
architecture using the counts on the detail payload and merges. There is
a test.

Related: `Tone::models_count` means the cross-architecture total when the
tone came from search, and the v1 count alone when it came from detail —
so a card can promise 223 models and the detail screen list 112.

## Commercial terms

The free tier grants OAuth plus *bounded* list endpoints;
`/tones/search` is separately rate-limited (100 req/min overall) and the
docs ask you to contact support before relying on it in production. The
UI opens on a shelf (trending / latest / favourites) rather than an empty
search box partly for that reason. Shipping the in-app search publicly
needs a conversation with TONE3000.

`ToneShelf::Trending` and `Latest` are currently served through the
search endpoint, because the `tone3000` crate does not expose the
dedicated `/tones/trending` and `/tones/latest` routes yet — so today
they cost quota that a shelf is supposed to avoid. That fix belongs
upstream, not in a second HTTP path here.

## Testing

`crates/signal/tone3000/tests/against_a_mock_catalog.rs` stands up a
wiremock catalog on a loopback port and drives the whole conversation:
sign-in, paging, the architecture merge, the image cache, and a download
from `model_url` through to a catalog entry carrying its creator and
licence.

## Getting a key

1. Log in at tone3000.com → **Settings → API Keys** → **Create API Key**.
   The `t3k_pub_…` value is the publishable key. (The secret key is a
   server-only credential for the non-PKCE flows; this integration does
   not use one, and must not ship one.)
2. Add `http://localhost:4040/tone3000/callback` to that key's allowed
   redirect URIs. Their demo notes localhost origins are allowed during
   development without registration, so this may already work — register
   it anyway, so the behaviour does not depend on a development-mode
   exemption.
3. `export SIGNAL_T3K_PUBLISHABLE_KEY=t3k_pub_…` before starting the
   engine, or bake it in at build time under the same name.

## Two ways to be authorized

A local TONE3000 session (sign in from the browser, stored per machine)
or a **linked FastTrackStudio account** — link TONE3000 once at
`auth.fasttrackstudio.app/account`, and every machine signed in to that
account can download without its own authorization. `SignInStatus.via`
says which: `tone3000` or `account`.

The local session is preferred when present: it is this engine's own and
needs no network to confirm. The broker is the fallback, and every reason
it can fail — no account, not linked, issuer unreachable — falls back to
the local session rather than failing the call.

The account half lives in `crates/signal/account`, built on architect's
`auth-client::oidc`. The engine serves `/account/callback` for the same
reason it serves the TONE3000 one.

Why bother, when the local session already works: TONE3000 rotates its
refresh token on every use, so a session copied between machines
invalidates itself. The issuer refreshes in one place and hands out
short-lived access tokens; a device never holds the refresh token.

## Still open

- **Redirect URIs beyond loopback.** `docs/tone3000-redirect-uri-question.md`
  is a drafted question to support@ about the two cases localhost does not
  cover: the browser remote on a *different device* from the engine (the
  redirect would target a private LAN address over plain HTTP), and iOS,
  which needs a custom scheme. Loopback covers desktop and the plugin,
  which is everything needed to test.
- **iOS deep link** (`ASWebAuthenticationSession`) for the redirect,
  where a loopback URI is not servable.
